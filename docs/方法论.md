# AI 时代的品牌视觉规范：方法论

本文说明 brand-kit 为什么这样设计。读者有三类：

- **人**：品牌负责人、设计师、开发、运营，想知道这套做法解决什么问题、怎么用、怎么改。
- **维护品牌库的 AI**：按本文的原则做事，操作步骤见 [`维护流程.md`](维护流程.md)。
- **在其他项目里使用品牌库的 AI**：按 [`接入指南.md`](接入指南.md) 获取和使用。

文中的例子都来自虚构的示例品牌 Acme（[`example/acme/brand.md`](../example/acme/brand.md)）。

## 1. 要解决的问题

传统的品牌规范是一本 PDF 手册。AI 开始参与设计、开发和内容生产以后，它有四个问题：

1. **AI 读不准**：颜色在色块图里，AI 只能估色；规则散在版面里，分不清哪条是定论、哪条是建议。
2. **数值有多份**：网站 CSS、App 主题、设计稿各抄一份色值，改了一处，其他地方不会跟着变。
3. **没有版本**：不知道哪一版最新，谁在什么时候改了什么。
4. **没人检查**：规范写了“白字不能放在浅色底上”，做出来的东西有没有违反，全靠人眼。

所以 AI 时代的规范要做到：**只有一份来源、机器能读、每条有状态、能自动检查、AI 有明确的入口和边界**。

## 2. 六个部分

```
原件     素材库里的 PSD、AI、视频、原图            只存不改，由设计师维护
  │      提取（维护者 AI 整理，人确认）
规范     <品牌>/brand.md、source-index.md          规则正文，人和 AI 都能读；每条能追到原件
  │      数值只在令牌里定义，正文引用令牌名
令牌     <品牌>/tokens.json                        DTCG 2025.10 格式 + 状态、渠道、出处
  │      brand-kit build 自动生成
产物     build/<品牌>/                             网站 CSS、Flutter 常量、带说明的完整 JSON
  │      各项目原样复制或引用，不手抄
校验     brand-kit check + checks.json + CI        每次合并请求自动检查，详见第 3.6 节
入口     AGENTS.md                                AI 先读这里：判断角色、按任务找章节、禁止事项、交付检查
```

每一部分只做一件事，下游从上游生成或引用，不手抄。

## 3. 七条原则

### 3.1 只有一份来源

规范只在品牌库这个 git 仓库里维护。文档系统、网盘、各项目里不另存副本，需要时放链接。允许的例外是原样复制 `build/` 里的生成文件，并在文件头写明来源版本。两份手写的规范一定会走样。

### 3.2 数值只在令牌里

颜色、字体、尺寸只在 `tokens.json` 里定义。`brand.md` 写令牌全名，需要写色值时，同一行必须写出对应的令牌全名。网站和 App 用 `build/` 生成的文件。`brand-kit check` 会逐行检查。

### 3.3 每条都有状态

规范里没定论的事情很多。如果一律写“待确认”，使用者不知道能不能用，结果是谁都不敢用。所以分三种状态：

| 状态 | 正文写法 | 令牌 `status` | 含义 | 要求 |
|---|---|---|---|---|
| 已确认 | 「已确认」 | `confirmed` | 负责人明确确认过 | 写确认人、渠道、日期 |
| 按现状执行 | 「按现状执行」 | `current` | 照现有物料的做法定下来，可以直接用，以后可能改 | 写出处 |
| 待处理 | 「待处理」 | `pending` | 有问题没解决，使用者不能自行决定 | 写卡在什么问题上 |

原则：**能按现状执行的，不要挂成待处理**。只有不处理会出问题的（版权、错误、缺少印刷文件）才算待处理。**只有人的明确答复才能变成已确认**，AI 的推断最多是按现状执行。

### 3.4 从素材里提取，不凭空设计

规范是“把已有物料的做法写清楚”，不是重新设计。每个令牌的 `source` 写出处，`source-index.md` 记录看过哪些素材、哪些没看到。没有素材依据的写“现有物料没有涉及”。素材之间互相矛盾时，列出各方，按现状执行（哪个渠道照哪个），给出建议，交给人决定。

### 3.5 用渠道写清楚边界

每个令牌都声明能用在哪些渠道：`web`、`app`、`marketing`、`print`、`device`。设备屏幕专用的颜色只标 `device`，就不会出现在网站 CSS 里；AI 做广告时只取渠道包含 `marketing` 的令牌。渠道把“这个颜色只能用在哪里”从一句容易被忽略的说明，变成了机器能执行的规则。

此外，AI 最容易出错的地方都要写成明确的规则，不能只写“注意美观”：

- AI 不能生成 logo 和字标，只能用原文件
- 正式产品名和禁用的旧名（`checks.json` 的 `names.forbidden`，正文出现会报错）
- 产品功能能说什么，以哪份产品说明为准
- 交付前逐条检查的清单

### 3.6 能让机器检查的就让机器检查

`brand-kit check` 检查以下内容：

- 令牌格式：类型、值格式、颜色分量和 hex 是否一致；状态、渠道、出处必填；引用要存在、不能循环，不能引用已弃用的令牌，也不能引用没导出到同一渠道的令牌
- 对比度：按 WCAG 2.x 计算，并由 `checks.json` 生成 `brand.md` 第 3.2 节的对比度表
- `brand.md`：
  - 正文里的色值和令牌名
  - 只用规定的三种状态说法
  - 没有填完的占位符
  - 没有禁用的名字
  - 章节齐全、顺序对
  - 变更记录格式对
- 所有 Markdown 文件：链接和锚点能打开，引用的素材路径存在
- 生成文件：`build/` 是否最新，有没有漏提交或多余的文件

人只检查机器判断不了的：构图、气质、产品外观对不对。

### 3.7 改动可追溯、有人把关

- 改动走分支和合并请求，由品牌负责人审批（CODEOWNERS 加分支保护）。
- 每次改动在 `brand.md` 的「变更记录」写一行。确认过的写“确认人，渠道，日期”，没确认的写“未确认”。
- 令牌不改名、不删除，要替换就用 `$deprecated` 过渡，见 [`版本与发布.md`](版本与发布.md)。

## 4. 两种 AI 角色

| | 维护者 AI | 使用者 AI |
|---|---|---|
| 在哪里工作 | 品牌库 | 其他项目（网站、App、广告、内容） |
| 做什么 | 从素材提取规范、更新令牌、新增品牌、处理确认结果 | 按规范做页面、配图、生图、文案 |
| 能改什么 | 品牌库全部文件；定论要人确认 | 不改品牌库，发现问题报告给人 |
| 入口 | 品牌库 `AGENTS.md` 第 5 节 → [`维护流程.md`](维护流程.md) | 品牌库 `AGENTS.md` 第 1–4 节 → [`接入指南.md`](接入指南.md) |
| 完成标准 | `brand-kit check` 通过；变更记录已写；合并请求说明了出处 | 交付检查清单逐条过；写明规范版本、用到的「按现状执行」条目、碰到的「待处理」事项 |

## 5. 和其他做法的对比

| 做法 | 问题 | brand-kit 怎么处理 |
|---|---|---|
| PDF 品牌手册 | AI 读不准；没有版本；数值靠估 | Markdown + 令牌，git 管理 |
| Figma 设计系统 | 适合设计师；文案、生图等非设计场景覆盖不到；AI 和代码读取要额外工具 | 令牌是 DTCG 格式，可以导入 Figma（Tokens Studio 等插件）；规则写在 Markdown 里，覆盖所有场景 |
| 只给 AI 写提示词 | 规则散在各项目的提示词里，各写各的 | 一个品牌库，各项目通过 `AGENTS.md` 引用 |
| 在线文档 | 适合阅读和评论，但不能被代码引用，容易出现多份 | 文档里只放链接 |

## 6. 局限

- 构图、气质、“好不好看”机器判断不了，仍要人看。正反示例图（`<品牌>/examples/`）能帮 AI 和人对齐标准。
- 印刷色（CMYK、Pantone）要实物打样才能定，打样前先标「待处理」。
- 规范准不准，取决于素材全不全。没看到的素材要在 `source-index.md` 里写明。
- 只支持 sRGB 颜色和 DTCG 的一部分类型（见 [`令牌规范.md`](令牌规范.md)）。排版组合（typography）、阴影等复合类型以后再加。
