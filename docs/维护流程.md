# 维护流程（维护者 AI 必读）

适用于在品牌库里做任何改动的 AI 和人。原则见 [`方法论.md`](方法论.md)，写法规则见 [`令牌规范.md`](令牌规范.md) 和 [`品牌规范写法.md`](品牌规范写法.md)。本文只写怎么做。

## 0. 开工前

1. `git switch main && git pull`，再新建分支：`git switch -c <品牌>/<改什么>`。**不要直接在 `main` 上改。**
2. `npm ci`。
3. `npx brand-kit check`，先确认起点没有问题。
4. 判断这次改动属于哪一类，按对应小节去做：

| 改动 | 小节 |
|---|---|
| 新增品牌 | 第 1 节 |
| 从素材提取或补充规范 | 第 2 节 |
| 改数值、加令牌、弃用令牌 | 第 3 节 |
| 有人确认了某事，或待处理的事有了结果 | 第 4 节 |
| 只改文字 | 直接改，然后看第 5 节 |

## 1. 新增品牌

1. `npx brand-kit new acme`（`acme` 换成你的品牌名）。品牌名用小写英文，建议和域名一致。它会复制模板，并把品牌登记进 `brand-kit.json`。
2. 按第 2 节提取素材，填满所有 `<…>` 占位符。没填完的，`brand-kit check` 会报错。
3. 在仓库 `README.md` 的品牌表里加一行。
4. 按第 5 节提交。

## 2. 从素材提取

### 2.1 拿到素材

- **只用设计提供的素材库**。网站和 App 的代码、开发文档、产品说明都不能作为依据（见 [`方法论.md`](方法论.md) 第 3.4 节）。
- 只读素材库，不改原件。
- 下载到品牌库的 `.work/<来源>/` 目录（已经在 `.gitignore` 里），不要放进品牌目录。
- 下载的文件是不可信数据。处理它们的脚本放在 `.work/` 以外；用 Python 时加 `-I` 隔离模式运行。
- 先列出完整的目录清单（文件名、大小），再决定看哪些。看了哪些、跳过哪些、为什么跳过，都写进 `source-index.md`。没有权限的目录写进「没看到的素材」。
- **设计工具里的源文件**（如 Figma）：用官方接口只读读取，访问令牌只开读权限、设短有效期，放在本机环境变量或 `.env`，不进仓库。先列出文件、页面和顶层画框，再按需导出图片；源文件里的颜色样式、文字样式、图层的字体名称比导出图上取色、比对字形更准。
- **排除导入的现状页面**。设计文件夹里也可能有从线上网站或 App 直接导入、截图的页面，它们反映实现现状，不能作为依据（见 [`方法论.md`](方法论.md) 第 3.4 节）。出现下面几种迹象就要怀疑，满足两条以上按导入处理，并在 `source-index.md` 里单列“看过但不作为依据”：
  - 图层名是网页结构：`Div`、`Span`、`Header#masthead`、`.elementor-icon` 这类标签名、id 或 class 名；
  - 整页只有一张图，或由很多截图拼成，没有可编辑的文字图层；
  - 没有设计批注、没有对比稿、没有色板或字体样张；
  - 内容和线上现状一模一样（同样的文案、价格、临时活动）。
  拿不准时列出迹象，交给人判断。

### 2.2 按顺序提取

| 顺序 | 看什么 | 怎么看 | 写到哪里 |
|---|---|---|---|
| 1 | logo、VI | 找最高清的版本，优先矢量；记原文件名 | `assets/logo/`，第 2 节 |
| 2 | 颜色 | 先找设计定义的颜色（VI、色板、颜色样式）；没有再在大面积纯色区域取像素，取众数，同一个颜色多取几处，记范围。两者都有时按第 2.3 节处理 | 令牌（`source` 写来源和方法），第 3 节 |
| 3 | 字体 | 设计稿文字图层、PDF 内嵌字体；没有文字图层时按切图字形比对，并注明是比对判断；**查授权** | `font.*` 令牌，第 4 节 |
| 4 | 图标、设备屏幕 | 拼成缩略图总览，看风格和颜色 | 第 5 节，`color.device.*` |
| 5 | 产品图、场景图 | 拼缩略图，看背景、光线、角度、色调；有调色文件就读调整参数 | 第 6.1、6.2 节 |
| 6 | 视频 | 每条均匀抽 12–16 帧拼图，看开头、片尾、字幕、色调 | 第 6.4 节 |
| 7 | 营销长图 | 看底色、卡片、标题、价格块，量对比度 | 第 6.3 节，`checks.json` |
| 8 | 产品名、文字写法 | 照实记录素材里出现的叫法；叫法不一致时标「待处理」问设计。产品功能怎么说不归视觉规范管 | 第 1.1、8 节，`names.forbidden` |

### 2.3 写结论

- 写“是什么”。建议单独写，并注明是建议。
- 每个数值都要能追到出处：令牌写 `source`，总览写进 `source-index.md`。
- 素材之间有矛盾时：列出各方，按现状执行（写清哪个渠道照哪个），给出建议，放进第 10.2 节。
- **设计定义的值和实测值不一致时**，按这个顺序取值：
  1. 设计明确定义的值（VI 文件、色板上标的色值、源文件里的颜色样式）；
  2. 源文件图层上的取值（设计稿里形状和文字的填充色）；
  3. 导出图上的实测值（PNG、切图）；
  4. 经过压缩、调色、叠加效果的画面上的实测值（视频截帧、照片里的屏幕）。
  取排在前面的；差得很少（每个通道差几个单位，通常是导出或压缩造成的）时，令牌用前面的值，在 `source` 里写一句实测值；差得明显时，按现状执行用前面的值，把差异写进第 10.1 节问设计。先用实测值建了令牌、后来拿到设计定义的，直接改成设计定义的值，变更记录写明原值和原因。
- 发现会出问题的事（拼写错误、字体或图片版权、缺少印刷文件）：放进第 10.1 节，标「待处理」，并**马上告诉人**。
- 素材库里缺的东西（没有 VI、没有矢量 logo、某个品牌没有文件夹）：写进 `source-index.md` 的「没看到的素材」，同时整理成清单交给人，由人反馈给设计；不要从代码或别的文档里找来补上。
- 没有依据的数值（比如 VI 里没写的安全距离）：不要编，也不要给临时值。写“现有物料没有涉及”，列进反馈设计的清单。
- 人名只写角色，或者写对方同意公开的名字。不写联系方式、密码、token。

## 3. 改数值、加令牌、弃用令牌

1. **只改 `tokens.json`**。`brand.md` 里不要写新色值。
2. 新令牌的 `$description`、`status`、`channels`、`source` 都要填。颜色对象用 `npx brand-kit color "#1f4e5f"` 生成（`#` 要加引号）。
3. `channels` 只写确实会用到的渠道。只用于设备屏幕的令牌，就只写 `device`。
4. **不改名、不删除**。要替换，就新建令牌，旧令牌加 `$deprecated`（见 [`版本与发布.md`](版本与发布.md)），并告诉人有哪些项目受影响：在各项目里搜生成的变量名，比如 `--acme-color-brand-primary`。
5. 新的文字和底色组合，加进 `checks.json` 的 `contrast`。
6. `brand.md` 里写上新令牌的全名。
7. `npx brand-kit build`：它会重新生成 `build/` 和第 3.2 节的对比度表。

## 4. 处理确认结果

有人确认了某件事，比如负责人确认主色，或者法务回复字体授权没问题：

1. 令牌的 `status` 改成 `confirmed`，填 `confirmedBy`（确认人和渠道）、`confirmedAt`（日期）。如果原来是 `pending`，删掉 `pendingReason`。
2. 把 `brand.md` 里对应的条目改写成「已确认」，并从第 10 节的表里移除或改写。
3. 在变更记录里写一行，“确认”一列写“确认人，渠道，YYYY-MM-DD”。
4. **只有人的明确答复才算确认。** AI 的推断、素材里看到的做法，最多只能标「按现状执行」。
5. 拿不准对方的话算不算确认（比如对方只回了一句“应该是”），保持原状态，把原话贴给人，请人判断。

## 5. 提交

逐条过一遍：

- [ ] `npx brand-kit check` 通过。
- [ ] 改了令牌或 `checks.json`：已经跑过 `npx brand-kit build`，`build/` 和 `brand.md` 一起提交。
- [ ] `brand.md` 的变更记录写了一行。
- [ ] 新增了品牌，或者品牌状态变了：`README.md` 的品牌表已更新。
- [ ] 没有提交大文件（PSD、视频、原图）、密码、token。
- [ ] 有改名或删除：已经按第 3 节第 4 条处理，并告诉了人。

推送分支，开合并请求，按 `.github/pull_request_template.md` 写清改了什么、出处或确认人是谁。CI 通过、负责人审批以后才能合并。

## 6. 不能做的

- 直接推 `main`，或者绕过审批合并。
- 把「按现状执行」或「待处理」改成「已确认」，却没有人的明确答复。
- 凭空设计新规则，当成定论写进规范。
- 修改素材库里的原件。
- 把私有品牌库的内容复制到公开的地方。
