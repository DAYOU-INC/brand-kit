# 采用指南：给自己的团队建一个品牌库

本文写给想采用 brand-kit 的团队。整个过程大约需要：搭建半小时，每个品牌的整理半天到两天，主要取决于素材的多少。

## 1. 建仓库

```bash
npx https://github.com/DAYOU-INC/brand-kit/archive/refs/tags/v0.3.1.tar.gz init my-brands
cd my-brands
git init -b main
npm install
git add -A && git commit -m "初始化品牌库"
```

`package-lock.json` 一定要提交：CI 用 `npm ci` 安装，没有锁文件会失败。

`init` 会生成以下内容：

| 文件 | 作用 |
|---|---|
| `AGENTS.md`、`CLAUDE.md` | AI 的入口，按角色分工 |
| `README.md` | 给人看的说明和品牌表 |
| `brand-kit.json` | 品牌列表 |
| `package.json` | 依赖 brand-kit，版本固定在一个标签上 |
| `.github/workflows/check.yml` | 每个合并请求都会运行 `brand-kit check` |
| `.github/pull_request_template.md` | 合并请求的检查清单 |
| `.github/CODEOWNERS.example` | 审批人配置示例 |
| `.gitignore`、`.gitattributes`、`.editorconfig` | 排除大文件，统一换行符和编码 |

建议把仓库设为**私有**：真实品牌的规范里通常有未发布的产品信息和内部问题。

## 2. 设置审批

1. 把 `.github/CODEOWNERS.example` 改名为 `CODEOWNERS`，填上品牌负责人。
2. 在 GitHub 仓库的 Settings → Branches 里，给 `main` 加分支保护：
   - 合并前必须开合并请求（Require a pull request before merging）
   - 必须有代码所有者审批（Require review from Code Owners）
   - 必须通过状态检查，把 `check` 设为必需（Require status checks to pass）
3. 这样改动规范和令牌都必须由负责人审批，CI 不通过就不能合并。

私有仓库使用 GitHub Actions 要占用组织的计费额度，先确认组织的付款方式可用，否则 CI 启动不了。

## 3. 加第一个品牌

```bash
npx brand-kit new acme        # acme 换成你的品牌名
```

然后按 [`维护流程.md`](维护流程.md) 第 2 节，从素材里提取规范。可以把这件事交给 AI 来做，给它的指令可以这样写：

> 读品牌库的 `AGENTS.md`，你是维护者。按 `node_modules/brand-kit/docs/维护流程.md` 第 2 节，从 <素材位置> 整理 <品牌> 的视觉标准。没把握的写成「按现状执行」或「待处理」，不要编。做完运行 `npx brand-kit build` 和 `npx brand-kit check`，然后告诉我待处理的事项。

做完后，负责人逐条审一遍第 10 节，确认过的按 [`维护流程.md`](维护流程.md) 第 4 节改成「已确认」。

## 4. 让其他项目用起来

品牌库是私有的，其他项目的人要有读权限；其他项目的 CI 要读它，由管理员配一个只读的 deploy key 或细粒度 token。

在每个用到品牌的项目里加一行说明，写法见 [`接入指南.md`](接入指南.md) 第 2 节。网站和 App 改为引用 `build/` 里生成的文件，具体做法见接入指南第 4 节。

## 5. 升级 brand-kit

1. 看 brand-kit 的 [`CHANGELOG.md`](../CHANGELOG.md)，确认有没有不兼容的改动。
2. 把 `package.json` 里的标签改成新版本，运行 `npm install`。
3. 运行 `npx brand-kit build` 和 `npx brand-kit check`，按报错修改。
4. 开合并请求。

## 6. 从示例开始

brand-kit 仓库里的 [`example/`](../example/README.md) 是一个完整的品牌库，放的是虚构品牌 Acme。如果不确定某样东西该怎么写，先看它是怎么写的。
