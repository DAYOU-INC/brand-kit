# 接入指南（使用者 AI 必读）

适用于在**其他项目**里使用品牌规范的 AI 和人：网站、App、广告图、社媒、详情页、包装、视频、AI 生图、产品文案。原则见 [`方法论.md`](方法论.md)。

## 1. 拿到规范

| 情况 | 怎么拿 |
|---|---|
| 本地已经克隆了品牌库 | 用之前在品牌库里运行 `git switch main && git pull --ff-only`；不在 main 上、或者有没提交的改动，先停下问人 |
| 有仓库权限，本地没有克隆 | `git clone <品牌库地址>`，以后每次用之前 `git pull` |
| 只想读一个文件 | 用 GitHub 命令行读单个文件：`gh api repos/<组织>/<品牌库>/contents/<路径> -H "Accept: application/vnd.github.raw"` |
| 没有权限（云端 AI、外部协作者） | 停下，告诉人需要开权限。不要凭记忆写，也不要从现有网站或图片反推规范 |
| 其他项目的 CI 要读品牌库 | 由人在品牌库配一个只读的 deploy key 或细粒度 token，CI 用它克隆；不要把 token 写进代码 |

品牌库通常是私有的。不要把它的内容贴到公开的地方：公开仓库、公开的 issue、社交媒体，或者第三方工具的公开分享链接。

## 2. 在你的项目里登记

在项目的 `AGENTS.md` 或 `CLAUDE.md` 里加一行，以后进这个项目的 AI 都能看到：

```markdown
- **品牌视觉标准**：改样式、做配图、AI 生图、写产品名之前，先读品牌库（<地址或本地路径>）的 `AGENTS.md` 和 `<品牌>/brand.md` 第 9 节。颜色、字体、圆角只用 `build/<品牌>/` 生成的文件；logo 只用 `<品牌>/assets/logo/` 的原文件。
```

## 3. 先读什么

1. 品牌库的 `AGENTS.md`。
2. `<品牌>/brand.md` 的第 1 节（正式名称）和第 10 节（待处理和按现状执行的事项）。
3. 再按第 9 节的任务表，读和任务相关的章节。

## 4. 按场景使用

### 4.1 网站

1. 把 `build/<品牌>/variables.css` 原样复制进项目。文件头已经写了生成它的 brand-kit 版本；你只能在最上面加一行来源注释 `/* 来自 <品牌库>@<提交号或标签> */`，其他内容不要改。
2. 项目自己的变量指向令牌变量，不再写死色值：
   ```css
   :root {
     --color-primary: var(--acme-color-digital-web-primary);
     --radius-card: var(--acme-radius-card);
   }
   ```
3. 品牌库更新后重新复制，看过 diff 再提交。
4. 如果项目现在用的值和规范不一样，**不要直接替换**：先列出差异告诉人，由人决定是改项目还是改规范。

### 4.2 App（Flutter）

原样复制 `build/<品牌>/<品牌>_tokens.dart`，在 `ThemeData` 里引用其中的常量。同样在文件头记来源版本，不要手改。渐变没有 Dart 常量，要从 `tokens.dtcg.json` 里取色标（`tokens.resolved.json` 里只有 CSS 写法的字符串）。

### 4.3 设计稿、广告、社媒、详情页、包装、设备界面

- 数值从 `build/<品牌>/tokens.resolved.json` 取，**只用 `channels` 包含当前场景的令牌**：广告用 `marketing`，包装用 `print`，设备屏幕用 `device`。
- 设计工具要导入令牌时，用 `tokens.dtcg.json`（DTCG 格式，只含导出且没弃用的令牌）。各插件对 DTCG 2025.10 对象写法的支持程度不一，导入后核对几个颜色。不要导入 `tokens.json`，里面有已经弃用、不导出的令牌。
- 版式按 `brand.md` 第 6.3 节；文字和底色的组合按第 3.2 节的对比度表，表里没有的组合用 `npx brand-kit contrast "#前景" "#底色"` 算。

### 4.4 AI 生图

- 用 `brand.md` 第 7 节的提示词，产品外观以第 1.1 节为准。
- 生成的图里不要有 logo 和文字，logo 后期贴原文件。
- 生成后人工核对产品外观（按键、旋钮、屏幕的位置和数量），不对就重新生成。

### 4.5 产品文案

产品名用第 1.1 节的正式名称。功能和参数以第 8 节指向的产品说明为准，规范只管视觉和语气。

### 4.6 碰到「待处理」

比如包装用的字体授权还没确认：停下，或者用规范允许的替代方案；交付时写明碰到了哪一项、你是怎么处理的。不要自己拍板。

## 5. 交付

1. 逐条过品牌库 `AGENTS.md` 里的交付检查清单。
2. 交付说明里写明：
   - 依据的规范版本：品牌库的标签，或提交号（在品牌库里运行 `git rev-parse --short HEAD`）
   - 用到了哪些「按现状执行」的条目（这些以后可能会变）
   - 碰到了哪些「待处理」事项，你是怎么处理的
   - 规范没覆盖到的地方，你做了什么假设

## 6. 规范不够用或有问题时

- 不要在你的项目里另定一套，也不要直接改品牌库。
- 告诉人：缺什么、在哪个场景缺、你建议怎么定。
- 人同意改规范后，切到品牌库，按 [`维护流程.md`](维护流程.md) 开合并请求；合并以后，再回到你的项目更新引用。
- 发现规范和实际物料不一致（比如网站颜色改过了），同样报告给人，不要自己判断哪个对。
