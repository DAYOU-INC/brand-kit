# 版本与发布

有两样东西要分别管版本：brand-kit 工具本身，以及各团队的品牌库。

## 1. brand-kit 的版本

按语义化版本号（主版本.次版本.修订号）发布，打 git 标签 `vX.Y.Z`，在 [`CHANGELOG.md`](../CHANGELOG.md) 里记录每个版本改了什么。

| 改动 | 版本号 |
|---|---|
| 新增校验规则，可能让原本通过的品牌库报错 | 次版本（0.x 期间）；1.0 以后升主版本 |
| 改变生成文件的格式或变量名、令牌格式不兼容 | 主版本（0.x 期间升次版本），CHANGELOG 里写明怎么迁移 |
| 修 bug、改文档、新增可选功能 | 修订号 |

1.0 之前，次版本之间可能不兼容。品牌库应该把依赖固定在某个标签的压缩包上（`https://github.com/DAYOU-INC/brand-kit/archive/refs/tags/v0.3.6.tar.gz`），不要跟着 `main` 走。用压缩包地址而不是 `github:` 简写，是因为后者会在 `package-lock.json` 里记成 SSH 地址，CI 里没有 SSH key 会装不上。

### 发版检查

1. `package.json` 的 `version` 改成新版本。
2. 下面几处的标签一起改成新版本：`templates/repo/package.json`、`example/package.json`、三个 Schema 的 `$id`、模板和示例里的 `$schema`、`templates/repo/AGENTS.md` 和 `example/AGENTS.md` 里的文档链接、`README.md` 和 `docs/采用指南.md` 里的安装命令。`npm test` 会检查这些地方是否一致。
3. `node src/cli.mjs build --root example`，提交 `example/build/`。
4. `CHANGELOG.md` 写新版本一节。
5. 合并后打标签 `vX.Y.Z` 并推送。

## 2. 品牌库的版本

- 每次合并到 `main` 就算一个版本，使用方用提交号引用。
- 一批重要的改动合并后（比如主色确认、新增产品线），打品牌标签 `<品牌>-vX.Y.Z`，比如 `acme-v1.2.0`，在合并请求或发布说明里列出改了什么。
- 品牌标签的版本号怎么升：

| 改动 | 版本号 |
|---|---|
| 令牌弃用、下游需要改代码 | 主版本 |
| 新增令牌、状态变化（比如变成已确认）、新增章节 | 次版本 |
| 只改文字说明 | 修订号 |

## 3. 弃用流程

令牌不能直接改名或删除，下游项目引用的是生成的变量名。要替换，按下面的步骤做：

1. 新建令牌。
2. 旧令牌加 `"$deprecated": "改用 <新令牌全名>"`，`channels` 保持不变，继续导出。这样 Dart 会给出弃用警告，`tokens.resolved.json` 会带上 `deprecated` 字段。
3. 在合并请求里列出受影响的项目（在各项目里搜索旧变量名），通知这些项目的负责人。
4. 至少经过一个品牌次版本，等下游都改完，再把旧令牌的 `channels` 改成 `[]`（不再导出），品牌版本升一个主版本。
5. 旧令牌保留在 `tokens.json` 里作为记录，不要删除。
